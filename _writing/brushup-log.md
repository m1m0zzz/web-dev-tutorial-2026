章ごとに、**確認したこと**（実際に動かして裏を取ったもの）と**選んだ方針**（判断が要ったもの）を残します。同じ検討を繰り返さないための記録です。

| このファイル | 執筆者側の見直しで確認したことと、選んだ方針 |

## 0章 イントロダクション

### 確認したこと

| 内容 | 方法 | 結果 |
|---|---|---|
| Cloudflare の無料枠 | [Workers](https://developers.cloudflare.com/workers/platform/pricing/) と [D1](https://developers.cloudflare.com/d1/platform/pricing/) の料金ページ | Workers 100,000 リクエスト/日、D1 は読み取り 500 万行/日・書き込み 100,000 行/日・容量 5 GB、静的ファイルの配信は無制限 |
| GitHub Actions の無料枠 | [GitHub の料金](https://docs.github.com/ja/billing/managing-billing-for-your-products/managing-billing-for-github-actions/about-billing-for-github-actions) | GitHub Free は Private リポジトリでも標準ランナー月 2,000 分・アーティファクト 500 MB |
| 参照用リポジトリを remote として足す方式が成立するか | 空のリポジトリを作り、実際に `git remote add` / `fetch` / `diff` / `checkout` を実行 | 履歴が無関係でも `git diff tutorial/chapter-04 -- <path>` が動く。`git checkout tutorial/chapter-02 -- .` で章のツリーを取り込める。`git show tutorial/main:docs/03_backend.md` で記事も読める |
| 上の方式で `git branch` が汚れないか | 同上 | ローカルの `git branch` は増えない（増えるのは `git branch -r` だけ）。`-t 'chapter-*' -t main` を付けると Renovate の作業ブランチを取ってこない |
| CI とデプロイのトリガ | `.github/workflows/*.yml` | `ci.yml` は `pull_request` と `main` への push。デプロイは `main` への push かつ `paths` が一致したときだけ |
| `chapter-01` ブランチの実在 | `git branch -v` と `README.md` | 実在する。0章の表だけが古かった |
| デプロイまわりの実機確認状況 | [`README.md`](README.md) の「未確認の事項」 | `wrangler login`、`d1 create`、GitHub Actions の実行、本番での通し動作が未確認 |

### 選んだ方針

| 論点 | 選んだ案 | 理由 |
|---|---|---|
| 完成コードのリポジトリと読者のリポジトリの関係 | **読者のリポジトリに `tutorial` という remote を足す**（別フォルダに clone しない） | 答え合わせが `git diff tutorial/chapter-04 -- <path>` の1コマンドで済み、記事が繰り返し勧めている「差分を読む」がそのまま使える。別フォルダ方式だとディレクトリ比較ツールの説明が増える |
| remote の名前 | `tutorial`（`upstream` にしない） | `upstream` は fork 元を指す慣習で、この記事は fork ではない |
| `git remote add` を書く場所 | 1.8（0章は役割の説明だけ） | リポジトリを clone した直後に置くのが自然 |
| 章とブランチの対応表 | README に一元化し、0章からは削除 | 2箇所にあり、実際に0章側だけが古くなった |
| 章の末尾 | 次の章へのリンクを置く（最終章を除く） | 表を消したぶんの導線 |
| 「任意)」節の扱いの説明 | 「読み飛ばして構いません」とは書かず、内容の説明に留める | 2.10 を飛ばすと5章の CI が落ちるため。決着は2章で（`brushups/0_codex-review.md` の「2章へ持ち越し」） |
| 所要時間の目安 | 書かない | 実測していない数字は書かない方針 |
| バージョンの確認コマンド | 書かない | 表はメジャーバージョンだけで足り、正確な値は参照用リポジトリの `package-lock.json` にある |
| 費用の書き方 | Cloudflare 側は数値を書かずリンクのみ、GitHub 側は Private の月 2,000 分を明記 | Private を指定しているのに Public 前提の記述しかなく、読者が迷うため |
| 完成版アプリの公開 URL | `TODO(執筆時)` のまま残す | デプロイが済めば埋まる。[README.md](README.md) の「未確認の事項」にも記載 |
| 「通しの動作を確認しています」の範囲 | 現状のまま | 実機確認を済ませてから判断する |
| 「執筆の一部に Claude を使用しています」 | 現状のまま | クレジットとしての一文。検証状況は「動作を確認したバージョン」の節が担う |
| Renovate | major と 0.x の minor を automerge の対象から外す | 記事がバージョンを明記しているため。`drizzle-orm 0.45` のように、semver 上は minor でも記事の記述が変わるものが4つある |

## 3章 Hono でバックエンドを作る

### 確認したこと

| 内容 | 方法 | 結果 |
|---|---|---|
| 本文の無い節がどれか | 全章の節を、行数・コードブロック数・本文行数で機械的に集計 | 3.3 / 3.4 / 3.8 / 3.9 / 3.11 が「扱うこと」の箇条書きだけだった |
| `/health` の実際のレスポンス | ローカルの API を起動して `curl -i` | `HTTP/1.1 200 OK` / `Content-Type: application/json` / `{"status":"ok"}` |
| 未定義のパス・メソッドの応答 | 同上 | Hono が `404 Not Found` を `text/plain` で返す |
| CRUD の実装 | `chapter-03:apps/api/src/index.ts` | 認証込みの最終形。3.8 の時点では認証がまだ無いので、`user_id` に仮の値を入れる形にする必要がある |

### 選んだ方針

| 論点 | 選んだ案 | 理由 |
|---|---|---|
| 3.3 | `/health` のコードと、Context・レスポンスの作り方・ステータスコードの指定を書く | 「`app.get()` によるルーティング」と箇条書きにするだけでは、何も分からない |
| 3.4 | `curl` の実行例と、実際の出力を載せる。HTTP メソッドとステータスコードの表も | 実際に起動して取った出力を使った |
| 3.8 の `user_id` | `CURRENT_USER_ID = 'local-user'` という仮の値を置き、3.10 で置き換える | `user_id` は `NOT NULL` なので、認証が無い段階では何か入れないと動かない |
| 3.8 の 404 判定 | `.returning().get()` が `undefined` かどうかで判定する形をそのまま採用し、**3.10 の認可にそのまま繋がる**ことを明記 | 「存在確認 → 更新」の2段階にしないことが、認可の実装の要になっている |
| 3.9 | 認証と認可の違い、セッションとトークン、ハッシュ化、自前実装しない理由を本文で書く | 「実装の前に概念を整理します」と書いておきながら、整理が箇条書きだけだった |
| 3.11 | `select()` に列を明示する理由を、この節の中心として書く | 3.8 では `select()` を引数なしで使っている。同じ書き方を join したテーブルにすると、メールアドレスまで公開 API から返る |
