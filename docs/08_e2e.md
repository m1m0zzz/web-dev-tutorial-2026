# 8 E2E テストを行う

[4章](04_test.md)の単体テストは、フロントとバックをそれぞれ独立して検証するものでした。E2E テストは、両者を実際に繋いだ状態で、ユーザーの操作をブラウザ上で再現して検証します。

## 8.1 Playwright のセットアップ

E2E テストのランナーには Playwright を使います。実際にブラウザを起動して操作するため、ブラウザ本体も一緒に入れます。

```bash
npm i -D @playwright/test
npx playwright install chromium
```

WSL では、ブラウザの動作に必要なシステムライブラリが足りないことがあります。その場合は `npx playwright install --with-deps chromium` を使ってください（`sudo` を求められます）。

**ルートの `package.json` にスクリプトを足します。** [5.2](05_deploy.md#52-github-actions-を構築する) の CI からも、この名前で実行します。

```json
{
  "scripts": {
    "test:e2e": "playwright test"
  }
}
```

**`-w` を付けないのは、E2E がフロントと API の両方にまたがるからです。** どちらか一方の workspace に属するものではないので、ルートに置きます。

**つまずきポイント**

> [!TIP]
> - **ブラウザは入っているのに起動しない場合も、足りないのはシステムライブラリです。** ブラウザを入れ直さずにライブラリだけ足すなら `npx playwright install-deps` を使います

## 8.2 2つの開発サーバーとデータベースを用意する

E2E テストは、ローカルの開発サーバー（`apps/web` と `apps/api` の両方を起動した状態）に対して実行します。

本番環境に対して実行する構成も考えられますが、デプロイ完了を待つ制御が必要になり、テストデータが本番のデータベースに残るという問題もあります。ローカル実行なら D1 のローカル環境が使え、**テストの実行を始めるときにデータベースをリセットできます。**

**注記**: この構成では「デプロイされた本番が実際に動くか」は自動検証されません。[5章](05_deploy.md)でデプロイしたあとの確認は手動になります。

リポジトリのルートに `playwright.config.ts` を置きます。

```ts
import { defineConfig } from '@playwright/test'

const WEB_URL = 'http://localhost:5173'
const API_URL = 'http://localhost:8787'

export default defineConfig({
  testDir: './tests/e2e',
  fullyParallel: false,
  workers: 1,
  // CI では HTML レポートも出す。失敗したときに Actions の artifact として持ち帰る
  reporter: process.env.CI
    ? [['dot'], ['html', { open: 'never' }]]
    : 'list',

  use: {
    baseURL: WEB_URL,
    // 失敗したときに原因を追えるようにする
    trace: 'retain-on-failure',
    screenshot: 'only-on-failure',
  },

  // フロントと API の2つを起動する。
  // ローカル D1 の作り直しは、サーバーを起動する前に同じコマンドの中で行う
  webServer: [
    {
      // E2E 専用の保存先を使う。開発中に作ったローカルのデータを消さないため
      command:
        'rm -rf apps/api/.wrangler/e2e && npm run db:migrate:local -w apps/api -- --persist-to .wrangler/e2e && npm run dev -w apps/api -- --persist-to .wrangler/e2e',
      url: `${API_URL}/health`,
      reuseExistingServer: !process.env.CI,
      stdout: 'ignore',
    },
    {
      command: 'npm run dev -w apps/web',
      url: WEB_URL,
      reuseExistingServer: !process.env.CI,
      stdout: 'ignore',
    },
  ],
})
```

設定の意味です。

| 項目 | 意味 |
|---|---|
| `baseURL` | 相対 URL の基準。これがあるので、テストに `page.goto('/signup')` と書けます |
| `workers: 1` | テストを1件ずつ実行する。**8件が同じローカル D1 を共有するため**、同時に書き込ませない |
| `fullyParallel: false` | 1つのファイルの中でも並行させない |
| `trace` / `screenshot` | 失敗したときだけ記録を残す |

`url` に指定したアドレスが応答するまで、Playwright はテストを始めません。API 側に `/health`（[3.3](03_backend.md#33-最初のエンドポイント-health)）を作っておいたのが、ここで効いてきます。

**データベースのリセットをどこでやるか**

**`--persist-to` で、E2E 専用の保存先を指定しています。** これを付けないと、`npm run dev` で開発中に作ったメモやユーザーが、E2E を走らせるたびに消えます。**テストのために手元の作業データを失うのは避けたい**ので、置き場所を分けます。

`globalSetup` でローカル D1 を消してはいけません。**`webServer` は `globalSetup` より先に起動する**ため、起動済みのサーバーが開いているファイルを消すことになり、以降のリクエストがすべて 500（`SQLITE_CANTOPEN`）になります。

上記のように、**サーバーを起動するコマンドの中で、起動前に消す**のが確実です。

ただし、これで消えるのは**サーバーを新しく起動したときだけ**です。`reuseExistingServer: !process.env.CI` を付けているため、ローカルで `npm run dev` を別のターミナルで動かしたまま `npm run test:e2e` を叩くと、Playwright は既存のサーバーを使い回し、**コマンド自体が実行されません**。前回のデータが残った状態でテストが走るので、`公開-abc` のようなユーザーごとに変わる名前を使って、テストどうしがぶつからないようにしています。CI では毎回新しく起動するので、この問題は起きません。

## 8.3 テストを書く

`tests/e2e/memo.spec.ts` に、8つのシナリオを書きます。

1. サインアップ → メモを作成 → 一覧に表示される
2. メモを編集 → 更新が反映される → 削除する
3. 未ログイン状態で `/`（自分のメモ一覧）にアクセス → ログイン画面にリダイレクトされる
4. ログアウト → メールアドレスとパスワードでログイン → 自分のメモが戻る
5. メモを公開に設定 → ログアウト → その URL に直接アクセスして閲覧できる
6. 非公開メモの URL に未ログインでアクセス → 404 相当の画面になる
7. 未ログインで `/public` にアクセス → 公開メモの一覧が表示され、非公開メモが含まれない
8. ログイン中にログアウトを押す → リロードせずにログイン画面へ戻る

**3と8が認証（誰であるか）、4〜6が認可（何を見てよいか）の確認です**（[3.9](03_backend.md#39-認証認可の基礎)）。単体テストでも認可は確認しますが、E2E では「ブラウザから実際にその画面に到達できるか」を含めて検証できます。ルーティングの設定漏れは単体テストでは見つかりません。

**4は、ログイン画面そのものを操作する唯一のシナリオです。** 他はすべてサインアップから始まるので、これが無いとログイン機能が壊れていても気づけません。

**Playwright の3つの用語**

| 用語 | 意味 |
|---|---|
| `page` | 各テストに渡されるブラウザのタブ。テストごとに独立しています |
| Locator | `page.getByRole(...)` が返すもの。**要素そのものではなく「探し方」**です |
| `await expect(locator)` | 条件が満たされるまで、一定時間くり返し確かめます |

**`expect` に `await` が付くのが、単体テストとの一番の違いです。** ブラウザの操作は非同期なので、クリックした直後には要素がまだ無いことがあります。`await expect(...).toBeVisible()` は**現れるまで待ってくれる**ので、`sleep` のような待ち時間を自分で入れる必要がありません。

セレクタは、`getByRole` や `getByLabel` のようなアクセシビリティに基づく指定を優先します。利用者が画面上で要素を見つけるのと同じ手がかりを使うためです。

```ts
import { expect, test, type Page } from '@playwright/test'

// 実行のたびに別のユーザーを使う（サインアップの重複を避ける）
const unique = () => Math.random().toString(36).slice(2, 8)

const signUp = async (page: Page, userId: string) => {
  await page.goto('/signup')
  await page.getByLabel('メールアドレス').fill(`${userId}@example.com`)
  await page.getByLabel('パスワード').fill('password1234')
  await page.getByLabel('表示名').fill(`${userId} の表示名`)
  await page.getByLabel('ユーザー ID', { exact: false }).fill(userId)
  await page.getByRole('button', { name: '登録する' }).click()
  await expect(page.getByRole('heading', { name: 'メモ' })).toBeVisible()
}

const createPost = async (page: Page, title: string, content: string) => {
  await page.getByPlaceholder('タイトル').fill(title)
  await page.getByPlaceholder('本文').fill(content)
  await page.getByRole('button', { name: '追加' }).click()
  await expect(page.getByRole('link', { name: title })).toBeVisible()
}

test('公開したメモは、ログアウトしても URL から読める', async ({ page }) => {
  await signUp(page, `u${unique()}`)
  await createPost(page, '公開する日記', 'みんなに見せる')

  await page.getByRole('link', { name: '公開する日記' }).click()
  page.once('dialog', (dialog) => dialog.accept())   // 公開の確認ダイアログ
  await page.getByRole('button', { name: '公開する' }).click()
  await expect(page.getByText('状態: 公開中')).toBeVisible()

  const url = page.url()
  await page.getByRole('button', { name: 'ログアウト' }).click()

  await page.goto(url)
  await expect(page.getByRole('heading', { name: '公開する日記' })).toBeVisible()
})
```

**掲載したのは1件だけです。** 残りは上の一覧を見ながら、同じ形で書いてください。完成形は `chapter-08` の `tests/e2e/memo.spec.ts` にあります。

`npx playwright test` で8つのシナリオがすべて通れば成功です。

**つまずきポイント**

> [!TIP]
> - **セレクタに CSS クラス名を使わないでください。** スタイルを変えるたびにテストが壊れます。`getByRole` や `getByLabel` を使います（`getByLabelText` は Testing Library の名前です。Playwright には無いので間違えないでください）
> - **ページ遷移の完了を待たずに入力すると、遷移前のページに書き込みます。** 一覧から詳細へ移動した直後に `getByPlaceholder('タイトル')` を触ると、一覧側の入力欄が先に見つかることがあります（どちらのページにも同じ placeholder があるため）。`await expect(page.getByRole('heading', { name: 'メモの編集' })).toBeVisible()` のように、**遷移先の目印を1つ待ってから**操作してください
> - **部分一致に注意してください。** `getByRole('link', { name: '公開-abc' })` は `非公開-abc` にも一致します。`{ exact: true }` を付けます
> - `window.confirm` を出す操作は、`page.once('dialog', ...)` を**クリックの前に**登録します

## 8.4 CI で実行する

[5.2](05_deploy.md#52-github-actions-を構築する) で作った3つのワークフローに手を入れます。

**`ci.yml` には、独立したジョブとして足します。** 単体テストより時間がかかるので、分けておくと結果が読みやすくなります。

```yaml
  e2e:
    name: E2E テスト
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7

      - uses: actions/setup-node@v7
        with:
          node-version-file: .nvmrc
          cache: npm

      # ジョブをまたいでは引き継がれないので、ここでも safe-chain を通す
      - name: Install safe-chain
        run: |
          curl -fsSL https://github.com/AikidoSec/safe-chain/releases/download/1.5.15/install-safe-chain.sh -o /tmp/install-safe-chain.sh
          echo "de0565e3d6346407a604e84e639e95fea8758748063da2216bbfdca5feda5dd2  /tmp/install-safe-chain.sh" | sha256sum -c -
          sh /tmp/install-safe-chain.sh --ci
          rm /tmp/install-safe-chain.sh

      - run: npm ci

      # ブラウザ本体と、動作に必要なシステムライブラリを入れる
      - run: npx playwright install --with-deps chromium

      - run: npm run test:e2e
        env:
          CI: 'true'

      - uses: actions/upload-artifact@v7
        if: failure()
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 7
```

**`deploy-api.yml` と `deploy-web.yml` には、単体テストの後・デプロイの前**に2ステップを足します。

```yaml
      - run: npm test -w apps/api

      # デプロイの前に E2E も通す
      - run: npx playwright install --with-deps chromium
      - run: npm run test:e2e
        env:
          CI: 'true'
```

**E2E が落ちればデプロイのステップには到達しません。** [5.2](05_deploy.md#52-github-actions-を構築する) で単体テストに対して行ったのと同じ考え方です。

**動かす**

```bash
git add .
git commit -m "test: E2E テストを追加する"
git push origin main
```

GitHub の Actions タブで **CI → E2E テスト**を開きます。CI でも8つ通れば成功です。デプロイ側のワークフローでも同じテストが走ります。

**つまずきポイント**

> [!TIP]
> - CI ではヘッドレスモードで動くため、ローカルで見えていた問題が見えなくなります。**失敗したときは `playwright-report` の artifact をダウンロードしてください。** ブラウザで開くと、失敗した箇所のスクリーンショットとトレースが見られます
> - **CI で HTML レポートを出しているのは、この artifact のためです。** ローカルでは `list` レポーターのままなので、`playwright-report/` は作られません
